## 2026-11-06: Фаза 1, каркас apps/web

Сделано:
- Next.js 16.4.5 (App Router, TS strict, Tailwind 4), npm. `cacheComponents` и `partialPrefetching` выключены: ISR и точечная ревалидация по плану, auth без Suspense-обвязки. Вернёмся к вопросу в Фазе 3.
- PostgreSQL 17 в docker compose (`apps/web/docker-compose.yml`), порт только на 127.0.0.1, пароль из `.env`.
- Prisma 6: полная доменная модель, миграция `init`.
- Auth.js v5 (Credentials, JWT 7 дней). Роль и `sessionVersion` перечитываются из БД при каждом запросе в `src/lib/dal.ts`, поэтому смена пароля или роли отзывает сессии сразу. `proxy.ts` только оптимистичный редирект.
- Безопасность: argon2id, пароль 10-128 символов, одинаковое время ответа для неизвестного email, лимит попыток входа (8 на email и 30 на IP за 15 минут, в БД, ключи хешированы), лимит регистрации, фиксированный redirect после входа, заголовки (CSP, HSTS в prod, X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy), `poweredByHeader` выключен, env валидируется Zod без вывода значений, регистрация не может создать owner.
- Инструменты качества: ESLint `complexity` 10, jscpd (0 клонов), Stryker (89% на validation и env), Vitest (18 тестов).
- Бэкап `npm run db:backup` и проверка восстановления `npm run db:restore-check` (дамп в `migration/private/backups`, вне git).

Проверено вручную на собранном приложении:
- неверный пароль не выдаёт cookie, верный выдаёт httpOnly cookie, `/profile` открывается;
- аноним на `/profile` получает 307 на `/login`;
- после повторного `create-user` (`sessionVersion` +1) старая сессия получает 307;
- после 9 неудачных входов правильный пароль тоже отклоняется;
- backup и restore дали одинаковое число таблиц и пользователей.

Известные ограничения и долги:
- `npm audit --omit=dev`: 3 high в `deepmerge-ts` через CLI Prisma (`prisma`/`@prisma/config`). Работает только при сборке, не от запросов. Лечится апдейтом на Prisma 7 (breaking), планируем в Фазе 2 вместе с адаптерами.
- CSP пока с `unsafe-inline` для скриптов (нужно Next для гидрации); nonce-CSP в Фазе 3.
- Лимит по IP использует `x-forwarded-for`: на проде нужен доверенный прокси, который его перезаписывает.
- Регистрация без подтверждения email и без капчи (Фаза 4); дубликат email отвечает общей ошибкой.
- Лимиты в БД покрыты только ручной проверкой, интеграционный тест с тестовой БД добавим в Фазе 2.
- Локальные тестовые пользователи (test@, owner@orientir.local) созданы с одним случайным паролем в временном файле, только для локальной БД.

Страницы пагинации WP-стиля: `/archive/page/N`, за последней страницей 404. `/wp-content/uploads/../.env` и `.php` дают 404.

Известные расхождения и пробелы:
- Галереи FooGallery не отображаются (`data-gallery` скрыт), форма контактов только заглушка (Фаза 4).
- Колонки из шорткодов Presso потеряны; архивы авторов (`/author/`) не реализованы (авторы не пользователи).
- `expiresAt` у записей не фильтруется; медиа-маршрут без Range.
- Меню динамическое: рубрики с >=5 записей; WP-URL со слэшем на конце редиректят (308) на вариант без слэша.
- В WP `/home` и `/blog` заменены на `/` и `/archive`.
- jscpd: 1 клон (одинаковый блок импортов в category/tag), принято.
- На Windows при сборке бывают предупреждения EBUSY по `.next/cache` (антивирус), на результат не влияют.

## 2026-11-06: изменение требований, без личного кабинета

Решение владельца: ЛК, регистрация и вход не нужны. Вместо них форма «Прислать материалы» (`/materials`): имя, контакт, название похода, рассказ, ссылка на фото.
Фотографии на сайт не загружаем. Сервис: Яндекс Диск (публичная ссылка, принимаются только https на disk.yandex.ru/by/com и yadi.sk). Позже фото подтягиваем из публичной папки через API Яндекс Диска (`/v1/disk/public/resources?public_key=`), это отдельный шаг в Фазе 5/6.

Удалено: Auth.js, argon2, страницы login/register/profile, proxy, DAL, модель User и enum Role, `Post.authorId`, `AuditLog.actorId`, `AUTH_SECRET`, `create-user.ts`. Тестовые пользователи (2) удалены миграцией.
Добавлено: модель `Submission` (статусы new/processed/rejected), миграция `drop_users_add_submissions`, серверное действие с Zod, honeypot, лимитами 5 отправок в час на IP и 100 в сутки всего. Текст хранится как plain text и никогда не рендерится как HTML.
Проверено вручную: форма отправляет, запись попадает в БД.
Остаётся: уведомление владельцу (email-инфраструктура решается до Фазы 6), просмотр и обработка заявок через Agent API (Фаза 5), импорт фото с Яндекс Диска.
Фаза 4 в прежнем виде (auth, профиль) отменена.
